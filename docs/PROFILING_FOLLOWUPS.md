# Profiling follow-ups

This note records possible future work. The current profiling contract is in [MCP.md](MCP.md#speculative-profiling).

- **Instrumentation isolation upstream:** Lean's profiler export mode retains traces by bypassing trace-to-message conversion, changing `#guard_msgs` behavior. Seek a supported collection API that preserves ordinary message semantics. Deferred declaration realization also captures options privately in the environment; seek an upstream way to separate profiler configuration from semantic declaration context. Until then, guards are unsupported with profiling and profiled handles require profiled continuations; do not rewrite private environment data or replay user commands to manufacture an unprofiled handle.
- **Task registration across backtracking:** Beam waits for the final reachable snapshot-task graph. Lean restores `snapshotTasks` during tactic backtracking, so an already-running child removed from that graph is not accounted for. Investigate lifetime tracking independent of semantic backtracking upstream; do not promise that an elapsed-time result proves all custom asynchronous work has settled.

- **Source attribution:** spans include a range only when Lean supplies one. Investigate whether an upstream Lean trace API can carry provenance to nested nodes. Do not infer child ranges from parent ranges or tactic labels.
- **Exclusive-cost summaries, later:** any subtraction must use the union of covered child intervals per thread and distinguish unrecorded child work from true self-time. Specify behavior under threshold filtering, omitted nodes, parallel work and truncation before publishing exclusive-cost fields. This work does not block an inclusive-only summary.
- **Rendering bounds:** selected summary labels use Lean's existing renderer. Output limits do not bound lazy evaluation. If stronger computation bounds become necessary, prefer an upstream rendering API to a second Beam pretty-printer. Do not infer source locations from rendered labels.
- **Collection metadata:** source code can change Lean profiler options, and Beam cannot detect every change. Investigate whether Lean can report effective per-node clock/threshold settings or missing-coverage reasons before designing a public result change. Consider distinct truncation reasons for span, visit and nesting bounds, clipped labels and incompatible clocks.
- **Heartbeat accounting:** investigate a request-local count alongside elapsed time. Define raw-counter versus `maxHeartbeats` units, inclusion of request-owned async tasks, nested limit resets and failure behavior. A parent-thread counter delta alone is not a declaration-wide total. Qualify repeatability on supported Lean versions before describing it as deterministic or directly comparable to a limit.
- **Existing-file profiling, targeted for 0.2.2:** discover expensive declarations without requiring callers to copy their source. Start from Lean's frontend and trace APIs, preserve project configuration, and keep file elaboration separate from full build latency.
- **Incremental-sync profiling, targeted for 0.2.2:** explain edit-to-diagnostics cost using version-associated observations collected before processing starts. Distinguish newly executed work, reused snapshots and work already underway; a sync wait is not a file elaboration measurement.
