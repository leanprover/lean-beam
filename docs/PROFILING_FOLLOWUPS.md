# Profiling follow-ups

This note records possible future work. The current profiling contract is in [MCP.md](MCP.md#speculative-profiling).

- **Source attribution:** spans include a range only when Lean supplies one. Investigate whether an upstream Lean trace API can carry provenance to nested nodes. Do not infer child ranges from parent ranges or tactic labels.
- **Compact summaries, inclusive first:** prioritize candidate comparison and hotspot inspection without client-side post-processing. Start with the existing elapsed total, individual recorded declaration-phase spans (such as `Kernel`, `Elab.def.maxSharing`, `addDecl`, `Elab.definition.value` and `Elab.lint`), and bounded top spans by inclusive duration with their recorded category/tag. Keep references to the retained spans. These observations need no child-time subtraction and need not wait for exclusive-cost semantics. Label durations as inclusive, preserve partial-coverage/truncation information, and do not sum overlapping phases into a breakdown or treat absent spans as zero cost. Categories are Lean-version-dependent; do not require every phase to appear. Keep access to full retained spans without requiring a new mode for ordinary probes.
- **Exclusive-cost summaries, later:** any subtraction must use the union of covered child intervals per thread and distinguish unrecorded child work from true self-time. Specify behavior under threshold filtering, omitted nodes, parallel work and truncation before publishing exclusive-cost fields. This work does not block an inclusive-only summary.
- **Readable labels:** investigate bounded labels for selected hotspots. A top-K output limit alone does not bound evaluating Lean's lazy message labels; characterize evaluation cost, failure, cancellation and effects first. Preserve the current guarantee that ordinary profile projection does not force lazy labels. Do not infer source locations from rendered labels.
- **Collection metadata:** source code can change Lean profiler options, and Beam cannot detect every change. Investigate whether Lean can report effective per-node clock/threshold settings or missing-coverage reasons before designing a public result change. Consider distinct truncation reasons for span, visit and nesting bounds, clipped labels and incompatible clocks.
- **Heartbeat accounting:** investigate a request-local count alongside elapsed time. Define raw-counter versus `maxHeartbeats` units, inclusion of request-owned async tasks, nested limit resets and failure behavior. A parent-thread counter delta alone is not a declaration-wide total. Qualify repeatability on supported Lean versions before describing it as deterministic or directly comparable to a limit.
